# RDP (3389)

---

## Overview

`Remote Desktop Protocol` (`RDP`) is Microsoft's protocol for remote access to Windows computers — transmitting **display and control commands via the GUI**, encrypted over IP networks.

- Works at the **application layer** of the TCP/IP model.
- Typically **TCP port 3389** (connectionless **UDP 3389** can also be used for remote administration).
- Installed by default on Windows servers (activated via Server Manager).
- Default security setting: connections allowed only to hosts with **Network Level Authentication (`NLA`)**.

#### Connectivity Requirements

- Both the network firewall *and* the server firewall must allow outside connections.
- With NAT in the path (typical for Internet connections): server needs a reachable public IP + **port forwarding** configured on the NAT router toward the server.

#### Encryption Reality

- TLS/SSL supported since **Windows Vista** — protects all data, especially login.
- ⚠️ But many systems don't insist on it and still accept inadequate encryption via **"RDP Security"**.
- Identity-providing certificates are **self-signed by default** → clients can't distinguish genuine vs. forged certs (just generate a warning for the user).

## Footprinting the Service

#### Nmap

```
tylapcheong@htb[/htb]$ nmap -sV -sC 10.129.201.248 -p3389 --script rdp*
```

What it reveals:

|**Script**|**Intel gained**|
|---|---|
|`rdp-enum-encryption`|Security layer support: `CredSSP (NLA): SUCCESS`, `CredSSP with Early User Auth`, `RDSTLS`|
|`rdp-ntlm-info`|Target/NetBIOS/DNS names (`ILF-SQL-01`), OS `Product_Version: 10.0.17763`, system time|

#### OPSEC Warning — Packet Trace Cookies

With `--packet-trace` you can inspect packets manually — and see that Nmap interacts using the **RDP cookie `mstshash=nmap`**:

```
Cookie: mstshash=nmap
```

Threat hunters and EDR solutions identify this cookie and can **lock us out on hardened networks**. Know that your standard scans are signatureable.

#### rdp-sec-check.pl

Cisco CX Security Labs Perl script — unauthenticated identification of RDP security settings based on handshakes:

```
# deps first
tylapcheong@htb[/htb]$ sudo cpan    # then: install Encoding::BER
tylapcheong@htb[/htb]$ git clone https://github.com/CiscoCXSecurity/rdp-sec-check.git && cd rdp-sec-check
tylapcheong@htb[/htb]$ ./rdp-sec-check.pl 10.129.201.248
```

Summarizes:
- **Protocol support**: `PROTOCOL_SSL` / `PROTOCOL_HYBRID` (uses NLA/CredSSP) / `PROTOCOL_RDP`
- **Encryption methods accepted**: NONE, 40BIT, 56BIT, 128BIT, FIPS
- Example hard target: only `PROTOCOL_HYBRID: TRUE`, all weak encryption methods unsupported

## Connecting

Linux clients: `xfreerdp`, `rdesktop`, or `Remmina`.

```
tylapcheong@htb[/htb]$ xfreerdp /u:cry0l1t3 /p:"P455w0rd!" /v:10.129.201.248
```

Expect a certificate warning — self-signed cert, name mismatch (`CN = ILF-SQL-01`). Accepting drops us into the server's desktop GUI after NTLM authentication.

## Workflow Cheat Sheet

1. Nmap `-p3389 --script rdp*` → NLA status, encryption layers, hostname, OS build via NTLM info
2. `rdp-sec-check.pl` → full protocol/encryption matrix (weak-method exposure)
3. Grab the leaked hostname/product version from `rdp-ntlm-info` even without valid creds
4. Connect with `xfreerdp /u:<user> /p:<pass> /v:<IP>` when credentials are available
5. On hardened targets, avoid stock Nmap probes — `mstshash=nmap` is an EDR signature
